# ADR-001: 個人開発バックエンドにおける「インフラ」および「フレームワーク」の選定

## ステータス (Status)
採択 (Accepted)

## コンテキスト (Context)
個人開発の超小規模Webアプリケーションにおいて、維持コストの最小化（月額0円運用）と運用負荷の削減が求められている。
現在のバックエンド資産は Java / Spring Boot（リフレクションを多用）で構築されている。

このアーキテクチャ設計においては、「どこで動かすか（インフラ）」と「何で動かすか（フレームワーク）」は相互に影響を与えるものの、本質的に解決すべき課題（インフラ運用コスト vs アプリケーションの実行効率・移行工数）が異なる。そのため、これらを2つの独立した意思決定セットとして評価・定義する。

---

## 意思決定 1: インフラストラクチャとデータベースの選定

### 評価対象
1. Cloudflare (Workers / D1 / KV)
2. AWS (App Runner / Lambda + DynamoDB)
3. GCP (Cloud Run + Firestore)

### 決定事項
**GCP (Cloud Run + Firestore)** を採用する。

### 理由・根拠
1. **実行環境の制約:** Cloudflare Workers (V8 Isolate) では既存の JVM (Spring Boot) をそのまま動かすことができず、コンテナ実行環境が必須となるため候補から外れる。
2. **コスト構造 (永久無料枠の優位性):** GCP の Cloud Run と Firestore は絶大な永久無料枠を持ち、アクセスが少ない個人開発規模であれば維持コストが物理的に $0 で完結する。AWS のコンテナサービス (App Runner 等) は常時少額の課金が発生し、DynamoDB はデータ転送料金 (Egress) の不確実性がある。
3. **運用負荷:** Firestore は事前プロビジョニングや複雑なインデックス設計（DynamoDBにおけるGSI等）が不要であり、Cloud Run もインフラ管理を完全に透過できる。

---

## 意思決定 2: アプリケーションフレームワークの選定

### 評価対象
1. Spring Boot (既存資産・通常 JVM 実行)
2. Spring Boot + GraalVM Native Image
3. Quarkus + Kotlin

### 決定事項
**当面は「既存の Spring Boot (通常 JVM 実行)」を維持**し、Quarkus への移行や GraalVM 化は見送る。

### 理由・根拠
1. **投資対効果 (ROI) の欠如:**
   「意思決定1」で GCP の採用を決定したため、Spring Boot の高いメモリ消費量であっても Cloud Run の無料枠（36万 GB秒/月）に十分に収まる公算が大きい。Quarkus へ書き換える工数（CDI、Firestore非同期処理への適応など）に対して、得られる金銭的リターンがゼロである。
2. **リフレクション・動的プロキシの制約回避:**
   GraalVM (Native Image) へのビルドは、既存の Spring 資産やサードパーティライブラリが持つ動的特性と相性が悪く、メタデータ設定 (`@RegisterForReflection`等) のメンテナンス地獄を招くリスクが高い。通常の JVM で動かすことでこの技術的負債を回避する。
3. **コールドスタート問題の局所化:**
   Spring Boot + Cloud Run の組み合わせで発生するスケール・トゥ・ゼロからの復帰遅延（数秒）に対する対策は、インフラ側および標準 JVM の機能向上によりカバー可能である（※詳細は後述の備考参照）。

---

## 評価と結果 (Consequences)

### 肯定的な影響 (Positive)
* **最小の工数で最大のコスト削減:** アプリケーション層をほぼ書き換えることなく、Docker コンテナ化するだけで AWS/VPS 等からのインフラ費用の劇的な削減（月額$0化）を実現できる。
* **関心の分離:** 「インフラはコンテナを動かすだけ」と割り切ることで、将来的に Quarkus や他の言語・フレームワークへ移行したくなった際のインフラ側のロックインが極めて少ない。

### 否定的な影響・トレードオフ (Negative / Risks)
* **初速のレイテンシ:** アクセスがない状態からの初回リクエスト（コールドスタート）において、Spring Boot の起動処理に伴う遅延が発生する。
* **Firestore API への結合:** JPA (Hibernate) 等の RDB 向け ORM から Firestore のドキュメントモデル・SDK へのデータアクセス層の書き換えは避けられない。この部分は、将来的に RDB 等へ戻す際の負債となる。

---

## 備考: 通常 JVM 環境（Cloud Run）におけるコールドスタート対策

GraalVM（Native Image）を利用せず、標準 JVM のまま Cloud Run 上での Spring Boot 起動遅延を緩和・解決するためには、以下のアプローチを採用する。

### JVM / フレームワーク機能による起動時間の圧縮（追加コストゼロ
数ドルの課金すら回避し、スケール・トゥ・ゼロ（完全無料）を維持したい場合は、以下の標準技術を組み合わせる。

1.  **AppCDS (Application Class-Data Sharing):**
    *   クラスのパース結果（メタデータ）を事前にアーカイブし、コンテナ起動時にメモリに直接マッピングする技術。Spring Boot 3.3 以降で公式サポートが強化されており、Dockerfile への数行の追加のみで起動時間を 20%〜30% 短縮可能。
2.  **Spring AOT (Ahead-of-Time) on JVM:**
    *   GraalVM を使わなくても、Spring Boot 3 の AOT エンジンを標準 JVM 向けに実行できる。起動時の動的な Bean スキャンや DI コンテナの構築処理をビルド時に事前生成された Java コードに置き換えるため、起動時の CPU 負荷とメモリ消費量を削減できる。
3.  **JVM 起動オプションの最適化 (Tiered Compilation):**
    *   起動コマンドに `-XX:TieredStopAtLevel=1` を付与する。JIT コンパイラの高度な最適化（C2コンパイラ）をスキップし、初速を優先する設定。小規模な個人アプリであれば、ピーク時のスループット低下よりも起動速度向上の恩恵が上回る。

*※論理的な補足: AWS Lambda の SnapStart で強力な解決策となる「CRaC (Coordinated Restore at Checkpoint)」は、基盤側のハイパーバイザー連携を必要とするため、現時点の GCP Cloud Run 上の標準コンテナ環境では第一選択肢とならない点に留意すること。*
