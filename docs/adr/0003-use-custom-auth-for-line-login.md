# ADR: LINEログインを用いた独自の認証アーキテクチャの選定

## Status
Proposed (提案中)

## Context
本プロジェクト（flight-checker）において、ユーザー認証としてLINEログインを採用し、自前バックエンド（Kotlin）と連携する構成を検討した。

当初は、LINEのトークンを用いてバックエンドからFirebase Authenticationのカスタムトークンを発行し、クライアントがFirebase SDKを用いてログインする構成も視野に入れていた。しかし、以下の状況が確認された。

1. **自前バックエンドの存在**: アプリの主要なロジックは自前のKotlinバックエンドAPIとして提供される。
2. **Firebase独自機能の不使用**: 通知にはLINE Messaging APIを利用する予定であり、FCM（プッシュ通知）やFirestoreへのクライアントからの直接アクセスなど、Firebase特有の機能をクライアント側で利用する見込みがない。

この状況下でFirebase Authenticationを認証（IdP）として挟むことは、クライアントアプリにFirebase SDKの導入を強いるだけでなく、ログインフローの多段化による実装の複雑性やエラーハンドリングの負担を不必要に増加させる懸念があった。

## Decision
Firebase Authenticationは利用せず、**自前バックエンド（Kotlin）による独自の認証・セッション管理**を採用する。

具体的な認証フローは以下の通りとする：
1. クライアントがLINEログインを実行し、LINEトークン（アクセストークンまたはIDトークン）を取得する。
2. クライアントが自前バックエンドのログインAPIにLINEトークンを送信する。
3. 自前バックエンドがLINEの検証APIを呼び出してトークンの正当性を確認し、LINEユーザーIDを取得する。
4. 自前バックエンドがユーザーの登録・更新（データストアとしての利用）を行う。
5. 自前バックエンドが独自のセッション情報（JWTまたはHTTP-only Cookieなど）を生成し、クライアントに返却する。
6. 以降、クライアントは自前バックエンドのAPIに対して独自のセッション情報を付与してリクエストを行う。

## Consequences

### Positive (メリット)
- **クライアント実装のシンプル化**: Firebase SDKの導入が不要になり、ログインフローが単一のAPIコールで完結するため、クライアント側の実装とエラーハンドリングが容易になる。
- **依存関係の削減**: システムからFirebase Authenticationという外部IdPの依存を排除できる。
- **柔軟性の向上**: 認証・認可のコントロールをバックエンドに完全に集約できるため、将来的な独自要件の追加に対応しやすい。

### Negative (デメリット)
- **バックエンドの実装コスト**: セッションの有効期限管理や、必要に応じたトークンのリフレッシュ（再取得）処理など、セッション管理の仕組みを自前で実装・保守する必要がある。

## Alternatives Considered
- **Firebase Authenticationを併用する案**: 
  バックエンドでFirebaseカスタムトークンを発行し、クライアントでFirebase SDKを用いてログイン、以降はFirebase IDトークンでAPI通信する構成。Firebase SDKによるトークン自動リフレッシュの恩恵はあるが、Firebaseの独自機能を利用しない本プロジェクトにおいては、クライアントの複雑性増加というデメリットが上回ると判断し、不採用とした。
